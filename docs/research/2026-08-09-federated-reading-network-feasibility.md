# 联邦阅读网络可行性简报

状态：初步调研（尚非产品或架构决策）  
调研日期：2026-08-09  
证据范围：W3C 与 IPFS 官方规范/文档；未将实现生态的事实当作协议保证。

## 结论

“让自托管服务彼此互联，围绕作品展开交流”不是伪需求：ActivityPub 正是为跨服务端分发社交活动而设计，能够承载身份、关注、书评、书单与评论。它也**不是**现成的“去中心化书籍分发系统”。把“联邦社交”和“受控书籍传递”绑成同一项首发承诺，会把两种风险混在一起。

建议将目标拆为两层：首发验证开放联邦阅读社区；作品文件的跨节点传递仅限明确可再分发的内容，并作为可选能力逐步验证。IPFS 适合作为不可变文件版本的内容标识与获取方式，不应被视为访问控制、版权合规、删除或持久保存方案。

## 已被标准直接支持的部分

| 能力 | 可行性 | 依据与产品含义 |
| --- | --- | --- |
| 跨实例身份与关注 | 高 | ActivityPub 以 Actor、inbox、outbox 表达账户；`Follow`/`Accept` 可建立关注关系。服务端到服务端通过向远端 inbox 投递活动连接社交图谱。[ActivityPub §1、§7](https://www.w3.org/TR/activitypub/) |
| 书评、短评、回复、点赞、转发 | 高 | `Create`、`Like`、`Announce`、`Undo` 及回复引用是标准活动/对象模式；可先用 `Note`/`Article` 发布，作品以稳定 HTTPS URL 引用。[ActivityPub §6–7](https://www.w3.org/TR/activitypub/) |
| 公开或仅关注者可见的书单 | 中高 | 地址字段与 followers collection 支持投递范围；但这是活动传播/展示约定，不等于可撤回的保密分发。[ActivityPub §6.1、§7.1](https://www.w3.org/TR/activitypub/) |
| 将一版 EPUB/PDF/TXT 绑定到不可变内容标识 | 高 | CID 由内容的加密哈希与编码信息构成；内容变化会产生不同 CID，相同内容在相同设置下产生相同 CID。[IPFS：CIDs](https://docs.ipfs.tech/concepts/content-addressing/) |
| 把文件上传机制纳入通用 ActivityPub 互操作 | 低 | ActivityPub 明确把二进制媒体上传的精确机制排除在本版范围外。因此 `ipfs://`、附件字段、书目字段、授权声明和读取体验必须由本项目定义 profile，其他实例不必理解它。[ActivityPub §6.12](https://www.w3.org/TR/activitypub/#uploading-media) |

## 关键缺口与风险

1. **互操作不是“用了 ActivityPub”就自然产生。** 标准允许扩展，但不定义“Book / Edition / ReadingProgress / Shelf”这些对象，也不规定封面、书目去重、版本、批注锚点或跨实现的书单语义。需要公开、版本化的应用 profile，并对最小对象及活动做兼容测试；否则只能保证收得到 JSON，不能保证语义一致。

2. **身份验证和实例信任是产品要设计的安全层。** ActivityPub 在标准化时没有强一致的认证机制；它要求接收端不要盲信声称来自其他来源的内容，并建议验证归属与更新权限。首发必须明确签名/密钥轮换的实现选择、对象来源校验、域名封锁与实例信任策略。[ActivityPub 安全考虑](https://www.w3.org/TR/activitypub/#security-considerations)

3. **联邦带来常规的滥用面。** 规范专门提示垃圾信息、跨实例拒绝服务、递归对象和富文本渲染风险；需要限流、队列重试与退避、对象/附件大小和解析深度上限、HTML 消毒、审核和封禁工具。[ActivityPub 安全考虑](https://www.w3.org/TR/activitypub/#security-considerations)

4. **撤回不是强制删除。** ActivityPub 的 `Delete` 只建议接收方移除本地表示，协议无法强制远端删除已传输内容；IPFS 的内容寻址与缓存会进一步放大这个边界。因此公开发布、撤回、举报和删除应承诺“本实例停止提供与发送撤回”，不能承诺“全网抹除”。[ActivityPub §7.4](https://www.w3.org/TR/activitypub/#delete-activity) [IPFS：持久化](https://docs.ipfs.tech/concepts/persistence/)

5. **IPFS 没有内置的私有书库语义。** 公共 IPFS 会公开 CID 与提供/获取它的节点元数据；未加密文件内容也是公开的。加密可保护内容，但密钥分发、成员变更、撤销后已获密钥的副本，以及阅读器兼容性都仍是应用责任。私有阅读进度、私有书目和受版权保护文件不应默认进入公共 IPFS。[IPFS：隐私与加密](https://docs.ipfs.tech/concepts/privacy-and-encryption/)

6. **IPFS 不保证可用性。** 缓存的数据可以被垃圾回收；需自行 pin 到至少一个受管理节点或使用可靠的持久化策略。CID 证明“拿到的内容匹配该 CID”，并不证明作者身份、授权状态或长期可访问。[IPFS：持久化](https://docs.ipfs.tech/concepts/persistence/) [IPFS：CIDs](https://docs.ipfs.tech/concepts/content-addressing/)

## 版权与本地治理边界

协议不判定一部作品是否可以再分发，也无法替实例执行法律义务。由于公开 IPFS 使未加密内容和相关 CID 可被网络参与者获取，产品默认不应把“用户已上传”理解为“用户有权公开发布”。

首发的可执行规则应为：仅允许发布**公版、开放许可，或发布者能确认拥有再分发权**的文件；每个公开文件须带机器可读的权利声明、来源/发布者声明、版本 CID 和投诉入口。实例管理员可以采用更严格的本地准入、屏蔽和下架规则；这一规则不试图改变任何司法辖区的法律结论。文学艺术作品受伯尔尼公约保护的基本框架可见 [WIPO 官方摘要](https://www.wipo.int/en/web/treaties/ip/berne/summary_berne)。

## 建议的最小可行联邦范围

**要验证的假设：** 读者愿意在可选择的实例上建立跨站身份与关注关系，并围绕可公开引用的作品获得比中心化读书社区更好的自主性与社区归属。

首发只实现：

- 一个实例上的账户（Actor）、公开资料、远端关注/取消关注；
- 发布与接收：作品卡片 URL、书评/短评、回复、点赞、转发、公开书单；
- 作品卡片的最小自定义 profile：稳定 HTTPS URI、标准书目字段、来源、权利状态、可选 `contentCid`、可选下载/阅读链接；
- 入站校验、签名/来源验证实现选择、队列重试、限流、大小限制、域名/用户封禁、举报与本实例下架；
- 私人阅读进度、私藏书目、上传原文件不参与联邦；不接公共 IPFS。

第二阶段才以小范围许可内容试点：文件先在发布实例受管存储并被 pin；活动只传播书目卡片与 CID/链接；接收方明确选择获取；记录声明而非把 CID 当成授权凭证。加密分发、付费内容、DRM、跨实例访问控制、全网删除和自动版权判定均不属于 MVP。

## 可行性判断

| 判断 | 置信度 | 原因 |
| --- | --- | --- |
| “联邦阅读社区”值得进入需求验证 | 高 | 核心社交交互与跨实例投递符合 ActivityPub 的既定模型。|
| “通过 IPFS 分发任意书籍”可作为产品默认能力 | 低（不建议） | 标准不提供授权、撤销、保密或持久性保证，且公开网络暴露内容与元数据。|
| MVP 可在不做区块链的前提下落地 | 高 | ActivityPub 与 IPFS 均不依赖区块链；首发只需前者，后者可完全延后。|

## 下一步：验证需求而非先建大系统

用 6–10 名目标用户和 2–3 个愿意自托管的社区做原型访谈/试用，重点检验四件事：他们为何不满足于现有读书社区；是否真的要自托管而非只要可迁移身份；是否会跨实例关注陌生读者；他们愿意公开的究竟是书评、书单还是文件。若“公开交流”成立而“自托管/跨实例”无人愿意承担运维，需求应收敛为可迁移数据的读书社区，而不是联邦产品。
