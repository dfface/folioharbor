## 4. 决策演进时间线

### 4.1 从旧数据库治理开始

最初目标是为 `ebooks-go` 开源做准备：

- 检查旧数据库设计是否合理；
- 核实 chapter 冗余和 redirect 机制；
- 清理冗余数据并迁移到更合理的表结构；
- 补齐 Annotation 之外所有表的数据库迁移；
- 只开源程序，不公开 ebooks 数据。

用户明确解释了“重复章节”的业务含义：不是两条原始 HTML 完全相等，而是一本书的后续章节完整包含前面章节的有效正文，因此治理结果应保留后续章节。

### 4.2 从“先治理旧库”改为“先建新系统”

讨论中先考虑过：治理旧数据，设计趋向最终版本的新表，然后直接迁移。

随后策略被修正为：

1. 先实现一个真正可用的私人图书馆；
2. 用真实产品流程验证最终模型；
3. 再治理和迁移旧数据。

原因是旧数据不应该反向决定新系统的核心模型。先定目标模型，再编写单向迁移，可以避免为了兼容旧结构继续保留 redirect、章节编号和大字段表等历史问题。

### 4.3 决定完全重写

- 旧项目不做渐进式改造。
- 新项目位于同一父目录下，路径为 `/Users/yuhanliu/Documents/projects/folioharbor`。
- 旧 `ebooks-go` 保持为只读调查和迁移来源。
- 新项目必须先完成系统需求分析、方案比较和书面规格，再开始代码实现。
- 设计过程采用 Superpowers Brainstorming 流程。

### 4.4 多用户、协作和企业权限成为第一版基础

产品不再被定义为单用户电子书阅读器：

- 第一版必须支持多用户；
- 支持邀请、协作和共享；
- 需要数据权限，而不只是简单页面访问控制；
- 权限系统按企业级隔离、审计和可扩展性设计；
- 内置 owner、editor、reader 三类角色。

### 4.5 简化顶层概念

曾考虑过 Instance、Organization、Workspace、Library 和“全部图书”多个层级。用户指出 Workspace 的定位难以理解。

最终收敛为：

- `Instance（实例）`：一次自托管部署，是运维与联邦节点边界；
- `Library（书库）`：唯一协作、数据隔离、权限、配额和搜索边界；
- “全部图书”：书库中的查询页面，不是领域实体；
- Shelf 或 Collection：分类视图，不复制书籍或文件；
- 不再引入与书库语义重叠的 Workspace。

### 4.6 解决同书重复上传和跨实例判同

“一本书只属于一个书库”的早期设想被否决，因为：

- 多个人会在各自书库上传同一本书；
- 相同文件不应保存多份字节；
- 书目不能因为书库不同而变成互不相关的复制品；
- 联邦书评需要判断远程对象是否指向同一作品；
- 权限和文件物理去重又不能混为一谈。

由此形成了书目、馆藏、逻辑副本和 Blob 分层的方向。

### 4.7 存储策略围绕低磁盘设备调整

最初考虑过解析 EPUB 后把章节永久写入数据库，以方便在线阅读和全文搜索。用户进一步提出：

- 低磁盘设备是否承担得起原文件加解包内容的双份存储；
- Android 下载一本书不能变成逐章下载；
- 是否还需要二次压缩。

最终结论：

- 保留完整原文件作为事实源和客户端下载单元；
- 不永久保存解包 EPUB；
- 在线阅读通过受控资源接口流式读取包内资源；
- 衍生缓存可以重建并通过 LRU 回收；
- EPUB、PDF 已压缩，不再做应用层二次压缩；
- 旧 HTML 的清理和打包留到迁移阶段。

### 4.8 技术栈与系统架构收敛

Go 与 Rust 均做过生态评估，最终选择 Rust。推荐基线为：

- Rust、Tokio、Axum；
- PostgreSQL 与 SQLx；
- 显式、带版本号的 SQL migration；
- TypeScript Web 前端；
- 未来 Kotlin / Compose Android 客户端；
- 本地文件系统与 S3 兼容对象存储；
- 可选 Meilisearch；
- 一个 Rust workspace、一个数据库、API 与 Worker 两个可独立运行的进程。

架构选择模块化单体加 Worker，不在第一版引入微服务、Kafka、RabbitMQ 或强制 Redis。

### 4.9 标准化纠偏

早期模型使用过 `Edition`、`Publication`、`Rendition`。用户担心这些概念不够标准化。

经 IFLA LRM 和 BIBFRAME 调研后，核心书目语义纠正为：

```text
Work → Expression → Manifestation → Item
```

书港扩展 Holding、Blob、ContentUnit 等实体，但明确标注为产品扩展，不冒充书目标准。外部接口分别对接 EPUB、Readium、OPDS、Web Annotation、OIDC、ActivityPub 和 ActivityStreams。

### 4.10 第一实施规格选择端到端纵切

比较过三种推进方式：

1. 端到端最小纵切；
2. 平台基础优先；
3. 内容阅读优先。

已确认采用第一种：先用两名用户、一个共享书库和一个 EPUB 验证身份、权限、上传、书目、存储、阅读、进度与下载的完整链路。第一纵切的详细范围仍需要逐节确认后才能成为正式规格。

## 5. 产品定位

### 5.1 当前定位

FolioHarbor 是一个面向个人、家庭和小型团队的开源、自托管私人数字图书馆。

核心价值包括：

- 用户控制自己的文件和阅读数据；
- 多用户但默认私密；
- 可创建个人或共享书库；
- 能上传、整理、阅读和下载出版物；
- 权限模型足够可靠，可承载家庭、团队和企业场景；
- 可在低资源设备上部署；
- 可以逐步扩展为相互连接的阅读社区。

### 5.2 开源边界

- 开源程序、数据库迁移、协议实现、部署材料和测试。
- 不公开现有生产 ebooks 数据。
- 新实例必须能从空数据库执行 migration 后独立运行。
- 旧数据迁移工具可以开源，但实际数据、迁移映射和可能受版权保护的内容不进入公共仓库。

### 5.3 名称

- 当前工作名称：`FolioHarbor`。
- 中文名称：`书港`。
- 名称意象：书籍在个人控制的港湾中保存，也可以在获得授权时与其他港口连接。
- `BookNest` 因已有多个阅读产品而放弃。
- `LeafNest` 因已有其他领域品牌而放弃。
- FolioHarbor 尚未完成最终商标、域名和软件包名称审查，因此当前属于已采用的项目工作名，而不是法律意义上的最终品牌确认。

## 6. 用户、身份与注册

### 6.1 用户和实例

- 一个实例支持多个用户。
- 一个用户可以加入多个书库。
- 用户身份属于实例，不属于单一书库。
- 系统管理员负责运维和策略，不默认获得用户内容读取权。

### 6.2 登录方式

第一版完整发行目标同时支持：

- 本地邮箱和密码；
- OIDC SSO，例如 Keycloak、Auth0、Azure AD 或兼容提供商。

面向 Web 与未来移动客户端时，应采用适合公共客户端的授权码流程与 PKCE。OIDC 身份和本地身份的绑定、冲突及恢复仍需正式规格细化。

### 6.3 注册策略

- 是否允许公开注册可配置，默认允许。
- 是否要求邮箱验证可配置，默认要求。
- 支持邀请、允许的邮箱域和注册频率限制。
- 本地注册、受邀注册和 OIDC 首次登录使用一致的书库配置规则。

### 6.4 个人书库

- 默认在首次成功登录时幂等创建个人书库。
- 每个用户在一个实例中最多有一个系统自动配置的个人书库。
- 受邀用户仍拥有个人书库，同时加入被邀请的共享书库。
- 管理员可以关闭自动创建。
- 关闭配置不删除已有个人书库。

## 7. 书库与协作模型

### 7.1 Library 的职责

Library 同时承担：

- 成员边界；
- 数据隔离边界；
- 权限和资源授权边界；
- 存储配额边界；
- 默认搜索边界；
- 馆藏组织边界；
- 审计上下文。

### 7.2 角色

第一版只开放：

- `owner`：管理书库、成员、馆藏、访问策略和配额范围内的内容；
- `editor`：导入、修改和整理馆藏，但不能执行所有者级管理；
- `reader`：浏览、阅读，并在允许时下载。

底层不是把角色写死成单个枚举分支，而是维护稳定权限目录、角色和角色权限关系。第一版不提供自定义角色 UI 或 API，以控制授权组合和测试规模。

### 7.3 分类与全部图书

- “全部图书”是当前书库中可访问 Holding 的查询视图。
- Collection、Shelf、书单或专题是分类关系。
- 将一本书加入多个分类不会复制 Holding、Item 或 Blob。

## 8. 企业级权限和数据隔离

### 8.1 三层防护

1. PostgreSQL RLS：提供书库级粗粒度隔离。
2. 统一应用授权引擎：对动作、主体、资源和上下文做一致判断。
3. 资源授权：表达特定用户、角色或未来群组对具体资源的附加访问权。

示例动作：

- `library.manage`
- `member.invite`
- `holding.view`
- `holding.edit`
- `item.read`
- `item.download`
- `resource.share`
- `resource.manage_acl`

### 8.2 安全原则

- 默认拒绝。
- API、后台任务、搜索结果和签名下载都必须执行同一授权语义。
- 搜索索引中的租户过滤不能代替服务端重新授权。
- 系统管理员不自动读取内容。
- 紧急访问采用 break-glass：必须给出原因、限时、留痕并可审计。
- 管理和安全事件进入追加式审计记录。
- 普通用户不能枚举没有可访问 Holding 的全局书目记录。

### 8.3 四层公开策略

以下能力完全独立：

1. 书目元数据是否可发现；
2. 正文是否允许在线阅读；
3. 原文件是否允许下载；
4. 是否向联邦网络发布。

公开元数据不意味着公开阅读或下载；本地公开也不自动触发联邦发布。

资源可见性曾收敛为 private、library、restricted、public 四类基础状态：

- `private`：仅资源所有者或明确主体；
- `library`：书库中具有相应动作权限的成员；
- `restricted`：只允许额外授权中列出的主体；
- `public`：无需书库成员身份即可发现，但仍受阅读和下载的独立策略约束。

`federated` 不属于可见性枚举，联邦发布始终是另一项状态和操作。

### 8.4 个人数据

- 阅读进度默认仅本人可见。
- 批注默认仅本人可见。
- 用户可在未来显式分享书评、批注或阅读活动。
- 移除书库 Holding 不应立即硬删除用户的阅读进度和批注，应先进入不可访问或可重新关联状态。

## 9. 标准化书目模型

### 9.1 WEMI 核心

```text
Work
└── Expression
    └── ManifestationExpression ── Manifestation
```

- `Work`：抽象作品。
- `Expression`：翻译、修订、删节、演绎、朗读、着色等表达。
- `Manifestation`：具体出版或分发形态，包括出版信息与技术特征。
- `ManifestationExpression`：支持选集、多语合刊等多对多情况。

EPUB、PDF 和音频包如果出版或技术特征不同，通常是不同 Manifestation。

### 9.2 馆藏、逻辑副本与字节

```text
Library
└── Holding ─────────────> Manifestation
    └── Item
        └── ItemAsset
            └── Blob
                └── BlobLocation
```

- `Holding`：某书库对某 Manifestation 的馆藏记录。
- `Item`：某书库实际管理的逻辑电子副本。
- `ItemAsset`：原文件、封面、补充文件等副本资产。
- `Blob`：不可变字节和内容哈希。
- `BlobLocation`：Blob 在本地文件系统或对象存储中的位置。

权限附着于 Library、Holding、Item 和资源授权，不附着于 Blob。

### 9.3 网文、漫画和有声书

`Edition` 无法清晰表达连载内容，因此改用 WEMI，并增加通用内容扩展：

```text
Expression
└── ContentUnit
    └── ContentRevision

Manifestation
└── ManifestationUnit
    └── ContentUnit + ContentRevision + Locator
```

- `ContentUnit` 可以表示卷、章、话、页、音轨。
- `ContentRevision` 表示连载内容或原生内容的修订。
- `ManifestationUnit` 表示某出版形态采用哪个内容修订、顺序和格式定位。
- 固定出版物可以有 fixed release mode。
- 连载内容可以有 continuing release mode，并具有 draft、ongoing、hiatus、completed、discontinued 等生命周期。

普通 EPUB 不因采用 ContentUnit 而必须逐章永久拆分存储。

### 9.4 标识符与同一性

- 内部实体使用不可变 UUID。
- 外部标识符使用独立关系记录 scheme、value、issuer、标准化值和来源。
- ISBN 通常标识 Manifestation，不应直接成为 Work 主键。
- 文件 SHA-256 只能证明字节相同，不能证明不同文件属于同一 Work。
- 标题、作者、ISBN、正文指纹和远程 URI 可以产生等价候选，但不能静默自动合并。
- 等价关系应具有 candidate、confirmed、rejected 等状态，并保存来源、置信度和审核者。
- 合并和拆分操作需要可追踪事件，保留旧标识符和别名。

### 9.5 书评和动态的目标

评价目标根据语义选择：

- 对作品整体的评价指向 Work；
- 对翻译、演绎或修订的评价指向 Expression；
- 对具体出版和排版质量的评价指向 Manifestation；
- 对某一章节、话或音轨的讨论可以指向 ContentUnit。

书评不附着在某个书库的 Item 上，除非评价讨论的就是该副本状态。

### 9.6 模型演进记录

讨论中的模型经历过以下变化：

1. 最初使用 `Work → Edition → Rendition → Blob`，并通过 `Library → Holding` 表示馆藏。
2. 为支持网文连载，`Edition` 一度被改为 `Publication`，并增加 fixed/continuing release mode 与生命周期。
3. 为表达翻译、修订、朗读和着色，引入 `Expression`。
4. 为避免“Publication 和 Rendition 共同承担 Manifestation”的非标准边界，最终采用完整 WEMI。
5. `Rendition` 不再作为核心书目实体；格式和文件职责分别进入 Manifestation、ItemAsset 与 Blob。
6. 早期 `HoldingRendition` 用于防止书库因共享书目而获得其他书库文件权限；在 WEMI 版本中，这一职责由 Holding 下的 Item 与统一授权承担。

这些旧名称只用于理解讨论历史，不能作为新数据库 schema 的兼容要求。

### 9.7 书库元数据覆盖与目录治理

- 全局书目保存规范化、可复用的目录事实。
- 书库可以通过 `HoldingMetadataOverride` 覆盖本地显示标题、封面、标签和简介，而不修改其他书库看到的规范记录。
- 目录数据需要 `record_sources` 保存来源和导入证据。
- `entity_aliases` 保存旧标识符、别名和被合并实体的入口。
- `merge_events` 保存目录合并、拆分或撤销的历史。
- `equivalence_assertions` 保存本地或远程的同一性候选、确认和拒绝结论。
- 本地覆盖与规范目录必须在 API 中明确区分，避免把用户自定义标题传播成全局事实。

## 10. 文件存储和空间策略

### 10.1 原文件是事实源

- 保存用户上传的原始 EPUB、TXT 或 PDF。
- 原文件用于重新解析、导出、备份和客户端下载。
- Android 离线阅读按整本原文件下载，支持断点续传、哈希和版本识别。
- 不采用逐章下载作为整本离线阅读的基础协议。

### 10.2 PostgreSQL 的职责

PostgreSQL 保存：

- 用户、会话、书库、成员和权限；
- WEMI 书目实体；
- Holding、Item、Blob 引用和存储位置；
- 内容目录与稳定 Locator；
- 导入任务和审计事件；
- 阅读进度、批注和业务状态。

PostgreSQL 不保存普通 EPUB 的完整解包资源副本。

### 10.3 缓存和解包

- Web 阅读器通过受控接口读取 EPUB 包内资源。
- 可以使用临时解包或条目缓存，但必须是可删除、可重建的 LRU 缓存。
- 缓存不能成为唯一事实源。
- 临时资源路径不能绕过权限检查。

### 10.4 压缩

- EPUB 本身是 ZIP 容器，不再二次压缩。
- 大多数 PDF 内部已有压缩，不再二次压缩。
- TXT 保留原始文件；是否产生标准化阅读版本属于导入产物设计。
- 旧 HTML 的清理和打包推迟到旧库迁移阶段。

### 10.5 存储后端

完整第一版必须同时支持：

- 本地文件系统；
- S3 兼容对象存储，包括 MinIO、AWS S3 和兼容实现。

第一端到端纵切可以先使用本地存储，但存储端口和数据模型不能依赖本地路径语义。

### 10.6 去重范围

曾提出三种可配置范围：

- 实例级去重：默认方向，最节省空间；
- 书库级去重：更严格隔离；
- 禁用去重：每次上传保持独立物理对象。

可使用类似 `storage_namespace + sha256 + byte_size` 的唯一语义表达不同范围。具体配置形式仍需在存储规格中确定。

### 10.7 垃圾回收

- 不维护容易漂移的手工权威引用计数。
- 根据真实 ItemAsset 或内容修订引用判断 Blob 是否可回收。
- 回收采用隔离、安全等待期和幂等删除。
- 一个书库删除 Item 不能删除其他书库仍引用的 Blob。

## 11. 上传、重复与导入

### 11.1 相同文件

- 同一书库已有相同原始 Blob 的有效 Item 时，上传是幂等的。
- 系统返回已有 Item，不创建重复 Holding 或书架条目。
- 上传尝试仍留下审计记录。
- 不同书库上传相同文件时分别拥有 Item，但可以复用 Blob。
- 将来若有独立授权副本需求，可以增加显式创建额外 Item 的高级操作。

### 11.2 相似书目

- 标题、作者、ISBN 或内容相似只产生匹配建议。
- 不自动合并 Work、Expression 或 Manifestation。
- 合并需要可审计、可撤销或至少可追踪的目录治理流程。

### 11.3 尚待设计

- 上传接收、哈希、验证、解析和发布的准确状态机；
- 损坏 EPUB、加密 PDF、未知 TXT 编码的处理；
- 导入失败文件的隔离期限和诊断下载权限；
- 元数据缺失与结构错误的严格程度；
- 防病毒或内容安全扫描的可插拔边界。

## 12. 存储配额

- 第一版必须支持书库级逻辑配额。
- 统计书库引用的原文件和永久衍生文件逻辑字节数。
- 跨书库 Blob 去重不减少各书库的逻辑用量。
- 临时缓存和可重建搜索索引不计入书库配额。
- 管理员可设置默认配额、单书库覆盖值和单文件上传上限。
- 存储适配器还需要实例级剩余空间保护。
- 上传前预检查，提交时再次确认，避免并发突破配额。
- 具体默认配额和单文件大小尚未确定。

## 13. 搜索

### 13.1 基础搜索

- 没有 Meilisearch 时仍可用 PostgreSQL 搜索书名、作者、标识符和基础元数据。
- 搜索默认在用户可访问的书库范围内执行。

### 13.2 Meilisearch

- Meilisearch 是可选、可重建的全文索引，不是事实源。
- 可以按书库启用。
- 索引文档包含稳定主键和书库过滤字段。
- 写入、删除和设置更新由后端管理凭证执行。
- tenant token 只能保护搜索端点，不能替代后端写入授权或返回内容前的权限复核。
- Meilisearch 更新是异步任务，需要记录 taskUid 并跟踪结果。
- 部分更新不会自动删除遗漏字段，索引同步必须区分替换、部分更新和显式删除。
- 全文索引以出版物内容单元或可定位片段为文档粒度，必须保存返回阅读器所需的稳定 Locator。

## 14. 阅读、进度与批注

### 14.1 Web 阅读

- 服务端暴露受控 Publication Manifest 和资源端点。
- 每次资源访问验证 Item、Holding、Library 和当前主体权限。
- EPUB CSS、字体、图片和内部链接需要在安全策略下保留阅读体验。

### 14.2 Locator

阅读位置使用 Readium Locator 风格结构：

- `href`
- `type`
- `locations.fragments`
- `progression`
- `position`
- `totalProgression`
- `text.before`
- `text.highlight`
- `text.after`

不同格式可以使用 EPUB CFI、HTML selector、PDF page 或媒体时间片段等扩展。只保存百分比不足以支持重新排版、搜索结果和批注恢复。

### 14.3 批注

- 采用 W3C Web Annotation 的 Body、Target、Selector 和 Motivation 语义。
- 内部可以使用关系列加 JSONB 保存标准对象与索引字段。
- 默认私有。
- 分享和联邦是显式后续动作。
- 阅读进度和批注应优先关联 Manifestation、ContentUnit 与 Locator，而不是只关联 Holding；用户从另一个有权访问的书库打开同一 Manifestation 时，可以继续自己的阅读状态。

## 15. 数据库迁移

### 15.1 否决模型驱动 AutoMigrate

不采用根据当前 Rust 结构体自动猜测数据库差异的 AutoMigrate，因为它难以可靠表达：

- 数据回填；
- 字段拆分或合并；
- 索引并发创建；
- 约束验证顺序；
- 可回滚或不可回滚的发布决策；
- 大表迁移的停机与锁风险。

### 15.2 采用显式版本化迁移

- migration 是按编号排序的 SQL 或受控迁移程序。
- 可以由 `folioharbor migrate`、容器初始化任务或部署流程自动执行。
- 使用 PostgreSQL advisory lock 防止并发迁移。
- API 启动时校验 schema 版本。
- 迁移可以自动运行，但不能自动推测。
- 从空数据库到当前版本必须始终可验证。

## 16. 系统架构

### 16.1 模块化单体

一个 Rust workspace 内按业务模块隔离：

- identity
- libraries / authorization
- catalog
- items / storage / downloads
- imports
- reading state / annotations
- search
- audit
- federation（后续）

模块通过明确接口和事务边界协作，不能跨模块任意修改表。

第一版唯一正式支持的关系数据库是 PostgreSQL。SQLx 使用 PostgreSQL 专用连接池和查询，不使用运行时 `Any` 驱动承诺多数据库兼容。模块边界用于隔离业务职责，不等于需要为 MySQL 或 SQLite 建立当前并不存在的适配器。

### 16.2 API 与 Worker

- API 处理身份、权限、目录查询、阅读资源和命令提交。
- Worker 处理导入、解析、封面与元数据提取、索引、缓存和 Blob GC。
- 两者共享代码库和 PostgreSQL，但可以独立部署与扩容。
- 后台任务使用 PostgreSQL 持久队列、锁、重试和幂等键。
- 第一版不引入消息中间件。

存储模块可以评估 OpenDAL 或自有适配器，但领域层只依赖稳定的对象读取、范围读取、写入、校验和删除端口；具体库选择尚未形成不可更改的决定。

### 16.3 前端与移动端

- Web 前端使用 TypeScript。
- Web 与 Android 使用相同 HTTP API、出版物清单和 Locator 语义。
- Android 计划采用 Kotlin / Compose。
- 移动端完整离线下载是未来规格，但服务端从一开始保留完整原文件和稳定内容版本。

## 17. 联邦与社区

### 17.1 联邦目标

希望形成类似 Mastodon 的互联阅读社区：

- 关注用户或主题；
- 发布书评、评分、书单和推荐；
- 发现其他实例的公开作品信息；
- 保持每个私人图书馆的数据主权。

### 17.2 协议边界

- ActivityPub 负责收件箱、发件箱、关注和活动分发。
- ActivityStreams 2.0 表达 Actor、Object、Activity、Collection 等对象。
- OPDS 2.0 表达公开或授权书目目录和获取链接。
- 书港扩展使用自己的版本化 JSON-LD namespace，不覆盖标准词义。
- WebFinger 可用于未来的联邦 Actor 发现；是否提供 NodeInfo 属于互操作规格中的后续选择。

### 17.3 默认不联邦的数据

- 书籍原文件；
- 私人书库和私人分类；
- 阅读进度；
- 私人批注；
- 未明确公开的成员或权限信息；
- 内部存储位置和下载签名。

### 17.4 跨实例作品判同

- 本地 UUID 是实例内身份。
- 远程对象使用稳定 URI。
- ISBN、DOI 等公共标识符作为证据，不作为唯一真理。
- 内容哈希只适用于精确字节匹配，不能跨不同格式代表 Work 身份。
- 实例可以交换 equivalence assertion，并保留来源、状态和置信度。
- 本地实例可以拒绝远程合并结论。

### 17.5 评分与信任范围

- 本地评分、中心站评分和信任范围内的联邦聚合应能区分。
- 用户需要知道评分来源和样本范围。
- 屏蔽、撤回、删除、更正、举报和审核决定必须能够传播或在本地覆盖。

### 17.6 中心评价站

未来可以建设“网文评价网”一类中心站点：

- 它是普通 ActivityPub 实例；
- 可以提供目录治理、作品匹配、趋势和社区入口；
- 可以成为可信数据源之一；
- 协议上不拥有不可替代的强制权威；
- 其他实例在中心站离线或消失时仍能独立工作；
- 本地管理员决定是否信任其等价关系、评分和审核信息。

## 19. 旧数据库真实调研

### 19.1 数据规模

调研对象为本机 PostgreSQL `127.0.0.1:5434`，数据库 `ebooks`，Schema `ebooks`，PostgreSQL 18.1。

| 对象 | 数量或大小 |
| --- | ---: |
| `book` | 39,108 行，约 422 MB |
| `chapter` | 5,134,239 行，约 25 GB |
| `annotations` | 3 行 |
| 有 redirect 的 chapter | 2,661,748 行，约 51.8% |

### 19.2 结构事实

- `chapter.id` 是主键。
- `(book_id, chapter_id)` 有唯一索引。
- 未发现重复 `(book_id, chapter_id)`。
- 数据中未发现孤立 chapter，但数据库本身缺少 chapter 到 book 的外键约束。
- 18 本书的 `book.total` 与实际章节数不一致，最大差值为 769。
- 3 本书最小 chapter_id 不是 0。
- 7 本书最大 chapter_id 不等于 `book.total - 1`。
- 38 本书存在 book 记录但没有 chapter。

### 19.3 redirect 事实

- 所有已统计 redirect 均指向同一本书中的后续章节。
- 未发现缺失目标、自重定向或向前回退。
- 旧阅读流程依赖 HTTP 302 跳转。
- redirect 源与目标原始 HTML 完全相等数为 0。
- 目标原始 HTML 直接包含源 HTML 的数量为 0。

上述两个 0 不否定业务上的正文包含关系，因为 HTML 模板、标签、样式和预处理会改变原始字符串。

### 19.4 治理规则

用户给出的目标规则是：后续章节若完整包含前面章节的有效正文，只保留后续章节。

正式删除前必须：

1. 使用与旧阅读器一致的正文抽取和规范化；
2. 去除模板、标签、脚本、样式和无意义空白差异；
3. 证明后章规范化正文完整包含前章；
4. 记录来源、目标、哈希、长度和判定证据；
5. 生成人工复核样本；
6. 在新系统中重建正确顺序，不迁移 redirect 补丁。

## 20. 旧数据迁移原则

- 新系统先稳定，迁移后进行。
- 旧库全程只读，使用快照或明确水位。
- 迁移是单向 ETL，不要求新系统继续运行旧 schema。
- 旧 book 映射为 Work、Expression、Manifestation、Holding 和 Item。
- 旧 HTML 在迁移过程中清理并包装为新系统支持的内容形态。
- 旧标识符到新 UUID 的映射永久留存。
- 迁移报告记录保留、合并、拒绝和人工复核数量。
- 验证章节顺序、正文哈希、书目数量、可读性和权限归属。
- 原旧库在验收结束前不删除。

## 21. 明确放弃或推迟的方案

### 21.1 已放弃

- 在旧 Go 项目上渐进式重构。
- 先把旧数据迁移到尚未被产品验证的“最终表”。
- 同时保留 Organization、Workspace 和 Library 三层租户概念。
- 把“一本书”直接归属于一个书库。
- 用一个 public 布尔值同时控制发现、阅读、下载和联邦。
- 用文件哈希充当 Work 身份。
- 把普通 EPUB 每章永久写成一份数据库正文或 Blob。
- 永久保存原 EPUB 和完整解包副本。
- 对 EPUB/PDF 再做应用层压缩。
- 根据 Rust 模型自动猜测数据库变更的 AutoMigrate。
- 第一版采用微服务和消息中间件。
- 第一版开放任意自定义角色。
- 只做内容阅读、以后再补多用户权限。
- 第一版同时维护 PostgreSQL、MySQL 和 SQLite 的等价实现。

### 21.2 已推迟

- TXT 与 PDF：完整第一版需要，第一纵切后扩展。
- OIDC 与 S3：完整第一版需要，第一纵切可先验证端口和本地实现。
- Meilisearch 全文搜索。
- W3C 批注完整能力。
- Android 客户端。
- 漫画、有声书和更多格式。
- 公开目录与公开阅读。
- ActivityPub 联邦。
- 中心网文评价站。
- 自定义角色。
- 旧数据治理执行与迁移。

## 23. 第一纵切当前草案

已确认的是“选择端到端纵切”，以下详细内容尚未完成逐节审批：

```text
本地注册与邮箱验证
→ 首次登录创建个人书库
→ owner 邀请第二位用户
→ 分配内置角色
→ owner/editor 上传 EPUB
→ Worker 验证并解析
→ 建立 WEMI、Holding、Item 和 Blob
→ 浏览书库与详情
→ 在线阅读并保存私人进度
→ 按权限下载原文件
```

拟包含：

- PostgreSQL 版本化 migration；
- RLS、统一授权和审计；
- 本地文件存储；
- EPUB；
- PostgreSQL 持久任务；
- Web 最小界面；
- 配额与重复上传幂等。

拟排除：

- OIDC、S3、TXT、PDF；
- Meilisearch、批注和公开目录；
- 联邦、自定义角色和旧数据迁移。

该范围必须继续经过架构、组件、数据流、错误处理和测试章节的逐段确认，才能写入正式规格。
